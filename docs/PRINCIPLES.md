# Принципы Booster

Постоянные правила проекта: что Booster делает и чего не делает никогда. Архитектура — `docs/ARCHITECTURE.md`, этапы — `docs/ROADMAP.md`.

## Продукт

Booster — десктопное приложение для Windows 10/11 x64: диагностика оборудования, драйверов и производительности; временный игровой профиль с гарантированным откатом; измерение FPS и доказательная оценка эффекта.

## Принципы

1. **Адаптеры и возможности**, а не отдельная программа под каждую видеокарту. Провайдеры сообщают, что умеют на конкретном железе и драйвере; Rules Engine выбирает оптимизации независимо от бренда. Новая модель GPU или новый источник телеметрии не должны требовать переписывать оптимизатор.
2. **Сначала измерение, потом изменение.** Каждое изменение обосновано диагностикой, его эффект проверен измерением.
3. **Каждое изменение обратимо** или явно помечено как необратимое. Снимок исходного состояния делается до изменения, восстановление — после игры и после сбоя.
4. **Система работает штатно — ничего не менять.** Не создавать видимость оптимизации.
5. **Не выдумывать данные.** Всё, что нельзя получить надёжно, помечается `Unknown` или «недоступно». Это касается скорости RAM, двухканального режима, температур, причин троттлинга, VRAM и т.п.
6. **Никаких обещаний фиксированного прироста FPS.** Выводы — только с оговоркой и только по повторным прогонам.
7. **Опасное — только вручную.** BIOS/UEFI, разгон, вольтаж, лимиты мощности, вентиляторы, XMP, тайминги и скрытые настройки драйвера — только диагностика и рекомендации.
8. **Booster сам не создаёт просадок.** Мониторинг лёгкий, частота опроса регулируется, тяжёлая диагностика запускается по запросу.
9. **Не вмешиваться в процесс игры.** Никаких инъекций, хуков, чтения памяти и оверлеев внутри игры.

## Модель безопасности действий

Уровни:
- **L0 ReadOnly** — инвентаризация и диагностика;
- **L1 Reversible** — временные настройки с надёжным откатом;
- **L2 Confirmed** — побочные эффекты, нужно подтверждение пользователя;
- **L3 ManualOnly** — только рекомендация.

Режимы в конфигурации:
- `allowed` — автоматически, только для L0 и строго проверенных L1;
- `optional` — выключено по умолчанию, пользователь включает сам;
- `ask-first` — подтверждение каждый раз;
- `recommend-only` — только рекомендация;
- `forbidden` — запрещено.

Правила:
- Автоматический профиль выполняет только L0 и проверенные L1. L2 и L3 никогда не применяются незаметно для пользователя.
- Неизвестное приложение или служба получает `recommend-only`, а не разрешение на автоматическое завершение.
- Состояние нельзя надёжно восстановить — действие нельзя включать в автоматический профиль.
- `ActionPolicy` — единственная точка принятия решения. `ActionExecutor` отказывается выполнять всё, что не прошло `ActionPolicy`.
- Каждое действие журналируется: что, когда, старое и новое значение, результат.
- Порядок для каждого изменения: сохранить старое значение → применить новое → зафиксировать успех.
- Статусы изменения: `Pending → Applied → Restored | RestoreConflict | RestoreFailed | NeedsReboot | NeedsManualCheck`. Сбой одного действия не мешает восстановить остальные.
- Запись журнала атомарная: временный файл, замена, сброс на диск.
- Восстановление не перезаписывает изменения пользователя. Текущее значение равно применённому Booster — вернуть исходное. Отличается — не трогать, пометить `RestoreConflict`. Восстановление идемпотентно.
- Ошибка на любом шаге Apply — откат уже применённого в обратном порядке.
- В активной игровой сессии допустимы только заранее подготовленные обратимые действия. Драйверы, BIOS, подкачка и всё, что требует перезагрузки, — подготовка до игры.

## Запреты: Booster никогда не делает автоматически

- «очистку RAM», выгрузку рабочих наборов, очистку standby list, отключение сжатия памяти;
- отключение файла подкачки, «универсальные» размеры вроде 1,5× RAM, изменение подкачки во время игры;
- массовое отключение служб; остановку защитных компонентов, RPC, сетевых служб, PnP, журналирования, Windows Update, управления устройствами, античита;
- отключение Windows Defender и создание исключений антивируса;
- приостановку процессов неизвестного назначения и завершение неизвестных приложений;
- реестровые твики из FPS-скриптов:
  - случайные значения `SystemResponsiveness` и `NetworkThrottlingIndex`;
  - массовые изменения MMCSS;
  - `GameDVR` и `GameConfigStore` без проверки версии Windows;
  - отключение телеметрии и служб «для ускорения»;
  - таймеры и планировщик;
  - глобальные графические параметры вместо настройки конкретной игры;
- глобальное максимальное энергопотребление или максимальное состояние CPU для всех устройств;
- установку драйверов и загрузку чего-либо из неофициальных источников;
- разгон, изменение вольтажа, лимитов мощности, вентиляторов, XMP, таймингов, прошивку BIOS;
- удаление кэша шейдеров перед игрой;
- переключение HAGS и настроек с перезагрузкой при каждом запуске игры;
- инъекции, хуки и чтение памяти процесса игры;
- подстановку выдуманных значений вместо `Unknown`.

## Безопасность машины разработчика

Во время разработки не выполнять команды, которые меняют систему: реестр, службы, схемы питания, файл подкачки, приоритеты процессов, драйверы, автозагрузку, HAGS. Это относится и к запуску «для проверки». Допустимы только read-only команды: `Get-CimInstance`, `powercfg /list`, `powercfg /getactivescheme` и т.п. Изменяющие действия проверяются только юнит-тестами на фейках; тесты на живой системе (`Category=Host`) только читают.

## Требования к коду

- `async`/`await` с `CancellationToken` везде; UI-поток не блокируется.
- Каждый внешний источник данных (WMI, нативные API, реестр, процессы, файлы, время) — за интерфейсом, чтобы в тестах использовать фейки.
- Исключения провайдеров не роняют приложение: деградация до `Unknown` с записью в лог.
- Никаких «магических» значений реестра и порогов в коде — только в конфигурации, с комментарием-обоснованием.
- Мониторинг по умолчанию не чаще раза в 1–2 секунды; собственное потребление Booster измеряется.
- Модули маленькие, у каждого одна ответственность.
- Зависимости проектов:
  - `Booster.Core` не ссылается на Platform и Providers; всё платформенное — за интерфейсами из Core;
  - классы `*Analyzer`, `*Matcher`, `*Engine` и расчёты живут в Core, сбор данных — в Platform.
- Nullable reference types включены; в `Booster.Core` предупреждения считаются ошибками.
- Конфигурация версионируется (`schemaVersion`) и мигрирует между версиями программы.
- Сторонние библиотеки и SDK:
  - перед подключением проверить лицензию и условия распространения;
  - нативные DLL загружать динамически: нет DLL — провайдер недоступен, приложение не падает.
- Метрики кадров везде считаются по одним определениям — см. `docs/ARCHITECTURE.md`, раздел «Метрики кадров».
- UI на русском, все строки — в `.resx`.
